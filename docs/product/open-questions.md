| Q-06 | Target platform / form factor: web, mobile, desktop, or API-first? | **RESOLVED** (PBD-0008; explicit Product Owner decision, 2026-08-19). Ordina's initial target platform/form factor is a **local, single-Trader desktop presentation surface**, running in-process against the existing Rust core, with no server-side persistence and no multi-user/external-beta assumptions at this stage. **Resolves platform/form-factor category only** — does not select a GUI framework, toolkit, or packaging model; does not authorize N-22 implementation; does not resolve or narrow Q-08, N-24, N-25, or F-8 (all remain OPEN); does not authorize server-side persistence, networking, accounts, or multi-user behavior. `docs/governance/identifier-ledger.md` PBD-0008. |
| W-1 | Well-Formedness vs canonicalization boundary — must a Strategy be canonicalized before Well-Formedness can be determined? | **RESOLVED** (ADR-0004 — ACCEPTED). **No.** ADR-0003's artifact-level ordering **Well-Formed → canonicalize → revision identity** is authoritative and unchanged; canonicalization of the Strategy artifact is **not** a precondition for determining Well-Formedness. A WF analysis may use a deterministic **local analysis normalization** that yields no revision identity, no canonical serialization, and does not supersede ADR-0003 canonicalization. Any normalization capable of affecting construct admission, a mandatory verdict, mandatory defect existence, Direction overlap/conflict/coverage, or defect identity/ordering is **contract-bound** to the applicable Canonical Semantic Contract and checker-semantics version. `adr/0004-strategy-well-formedness-evaluation.md` §7. |
| W-2 | Does the Well-Formedness result depend on a checker-semantics version, and is it the same version as the runtime evaluator's? | **RESOLVED** (ADR-0004 — ACCEPTED). A **Well-Formedness-checker semantics version** exists as an architectural concern and **every WF result is bound to the checker-semantics version that produced it**. Its scope covers every semantic rule whose change can alter an authoritative WF result, and it **encompasses and binds the applicable Canonical Semantic Contract version**. It is conceptually **distinct** from the runtime evaluator-semantics version; **N-24 remains OPEN** and owns that. No version syntax, persistence, serialization, or schema selected. `adr/0004-...` §8. |
| W-3 | How is ADR-0002 §10c construct admission operationalized — is decidability sufficient? | **RESOLVED** (ADR-0004 — ACCEPTED). Decidability is **necessary but not sufficient**. Each construct is dispositioned into exactly one of **structurally checkable / semantically analyzable / genuinely runtime-only / inadmissible**, and a construct is admissible only if every required WF analysis is **decidable**, **terminating**, and **tractability-bounded** (a bounded compositional traversal of the declared canonical construct, at most polynomial in declared construct size; no enumeration of an undeclared/implicit combinatorial state space). Unbounded or undecidable required analyses make the **construct type INADMISSIBLE** — never deferred to runtime and never merely UNUSABLE. A contradictory *instance* of an **admitted** construct is a mandatory WF defect → **UNUSABLE**, not inadmissible. The bound is architectural, not an implementation resource budget. `adr/0004-...` §4. |
| W-4 | What guarantees that the Well-Formedness checker and the runtime evaluator interpret an admitted construct the same way? | **RESOLVED** (ADR-0004 — ACCEPTED). A named architecture-level **Canonical Semantic Contract** — the authoritative operational semantics for every admitted canonical construct — is introduced, and both the ADR-0004 checker-semantics version and the future N-24 evaluator-semantics version **must be conforming realizations of the same applicable Contract**. **Checked semantics ≠ evaluated semantics is architecture-forbidden.** The Contract is not an evaluator, parser, library, VM, solver, language, or serialization format; **N-24 remains OPEN** and retains the evaluator-versioning decision. `adr/0004-...` §9. |
| W-5 | When multiple Well-Formedness defects exist, does checking fail fast or aggregate? | **RESOLVED** (ADR-0004 — ACCEPTED). **Aggregate, not fail-fast**, with **per-check prerequisite satisfaction — not stage membership — as the blocking criterion.** A mandatory check runs whenever *its own* semantic prerequisites hold; an unrelated failure must not suppress an independently-computable check. All independently-computable mandatory defects are collected; a check whose own prerequisites fail is **not evaluated** and is recorded deterministically as diagnostic metadata (`not-evaluated: prerequisite <defect-id> failed`), never as an invented defect. The verdict is UNUSABLE if any **evaluated** mandatory invariant fails; skipped checks can never make an invalid Strategy Well-Formed. No UX designed — **N-22 remains OPEN**. `adr/0004-...` §11, §10. |
| N-23 | Strategy rule-language expressiveness / decidability boundary? | **RESOLVED** (ADR-0002 — ACCEPTED). The canonical Strategy semantic model is a **Hybrid Typed Semantic Model over a constrained, non-Turing-complete semantic fragment**. Only constructs for which every Strategy-Well-Formedness-required analysis is decidable under the declared semantics may enter the canonical model; **undecidable canonical constructs do not defer to runtime — they are not valid canonical constructs**. Continuous raw evidence is permitted; the finite/analyzable requirement applies to the **logical Direction-outcome partitions**, not the raw evidence domain. `adr/0002-canonical-strategy-semantic-model.md` §10, §10c. |
| N-26 | Stable rule/node identity model? | **RESOLVED** (ADR-0003 — ACCEPTED). **Dual-identity architecture:** a **lineage identity** for provenance/explanation/evolution and a content-addressed **revision identity** for reproducibility; lineage is revision-qualified and denotes authorship continuity, not semantic sameness; explicit copy/clone (new lineage) and move/re-parenting (lineage persists; revision forks iff an identity-bearing property changes) behaviour. `adr/0003-canonicalization-and-revision-identity.md` §9. |
| N-27 | Does revision identity bind the canonicalization version? | **RESOLVED — YES** (ADR-0003 — ACCEPTED). Revision identity binds both the semantic-model version and the **canonicalization version**; a change in canonicalization rules must not silently re-identify an existing revision. `adr/0003-...` §6 (I6). |
| N-28 | Numeric precision / units identity semantics? | **RESOLVED** (ADR-0003 — ACCEPTED). Precision and units are identity-bearing **only when semantically operative**; when operative they are represented explicitly and never inferred from presentation. **Dimension is identity-bearing**; normalization occurs only within the same declared dimension; dimensionally-distinct quantities never canonicalize together; no lossy rounding/conversion is introduced. `adr/0003-...` §6. |

| Q-11b | How does a Strategy declare blocking vs. temporary conditions? | **RESOLVED** (RFC-0001 / PBR-0003). | Q-10b | How does a Strategy declare its own required evidence? | **RESOLVED** (to the extent accepted by RFC-0001 / PBR-0003). | N-19 | Is Strategy Well-Formedness a product concept? | **RESOLVED** (RFC-0001 / PBR-0003). A Strategy must pass a named deterministic pre-use **Well-Formedness** gate before entering Decision Validation. Failure means **UNUSABLE** — never READY, WAIT, or DO NOT TRADE (those are runtime Decision Validation statuses). Ordina may report/explain defects and request Trader correction; it may **not** silently repair missing operative Strategy semantics. RFC-0001 §12. |
| N-20 | Configuration change vs. Strategy revision? | **RESOLVED** (RFC-0001 / PBR-0003). A change within a parameter's explicitly declared permitted adjustable bounds may be treated as a **Decision Input** (invalidates READY where applicable, requires re-validation, no new revision necessarily). A **Strategy revision** is required for changes to operative definitions — rules, parameter bounds, condition classification, Direction logic, candidate-value derivation, applicability, or other operative semantics. Historical decisions remain bound to the exact revision used. No persistence architecture implied. RFC-0001 §14. |
| N-21 | What is the sufficient-Direction-logic criterion? | **RESOLVED** (RFC-0001 / PBR-0003). Direction logic is sufficient when explicit deterministic Strategy rules can produce exactly one valid Direction for every relevant reachable state where Direction is required, or the decision remains non-READY for another valid reason. **No Direction yet** (temporary evidence incomplete) is a runtime condition eligible for WAIT; **structurally insufficient Direction logic** (cannot deterministically produce Direction for a reachable required state) is a Well-Formedness failure → **UNUSABLE**, not WAIT and not DO NOT TRADE. Conflicting Direction rules are also Well-Formedness failures. No formal-verification tooling implied. RFC-0001 §15. |
